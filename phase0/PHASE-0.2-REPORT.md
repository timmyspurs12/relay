## 3. What I could still establish, and its weight

Blocked from the site, I went to the only live sources available: the module documentation (reachable via the page-fetch tool even though the sandbox blocks direct egress) and published package internals. Four findings changed something.

### 3.1 The validator payload shape is now confirmed — Phase 0 uncertainty #7 closed

The `jira:workflowValidator` reference documents the exact argument passed to a lambda:

```json
{
  "issue": { "key": "work-item-key" },
  "configuration": {},
  "transition": { "from": { "id": "…" }, "to": { "id": "…" }, "modifiedFields": { … } }
}
```

`extractIssueKey()` already handles `issue.key`, so no code change was needed — but this was an open risk in `VALIDATION-REPORT.md` §10 and it is now closed by documentation rather than guessed.

Two supporting details from the same page: `modifiedFields` are only attached if `read:jira-work` is granted (already in our manifest), and the returned `errorMessage` is what Jira shows the user — the manifest-level `errorMessage` is documented in the context of *expression* validators. Our probe returns a dynamic message, which is the operative path.

### 3.2 A documentation contradiction about `resolver` — recorded, not resolved

The validator's property table marks **`resolver` as Required = Yes**. But the same page's own example omits it:

```yaml
jira:workflowValidator:
  - key: my-forge-workflow-validator
    name: Project is PRO validator
    function: validate
```

…and the `@forge/manifest` JSON Schema does not list it as required either (required: `description`, `name`, `key`).

**Decision:** leave it out. Two independent sources (schema, official example) agree, and `resolver` is for rendering `create`/`edit`/`view` config resources, which the probe does not declare. **Risk:** if deploy rejects the manifest for a missing resolver, the fix is three lines. This is the first thing to watch on T1.

### 3.3 The condition module is confirmed dead by a third source

The condition's property table lists `expression` as required, `evaluateAgainstOriginalIssue`, `projectTypes` — and **no `function` at any point**. That is now three agreeing sources: the JSON Schema (two versions), the docs, and a third-party live probe published in August 2026 which set a condition's `expression` to `false` while its `function` returned `true`, and observed the transition disappear from `GET /issue/{key}/transitions` and a forced POST return `HTTP 400` — with the *validator's* message, not the condition's.

That last item is the closest thing to live evidence in this report and it is **not ours**. I record it as third-party observed, corroborating, and not a substitute for T2–T7.

### 3.4 The uninstall hazard has supporting (old) evidence and no authoritative answer

Jira Cloud issue **JRACLOUD-23885** describes exactly the situation: when a plugin supplying a condition, validator or post function is removed or disabled, "no warnings are visible in the UI though the transitions do appear", and steps using that transition "will not render any of the possible transitions".

It is an old, closed suggestion rather than current product documentation, so it is **indicative, not authoritative**. It points the same way as my expectation: a missing rule is treated as unmet, so Relay going away can block a customer's closure transition.

I am not going to upgrade "expected" to "confirmed" on the strength of a stale issue ticket. **T10 and T10b exist to settle it.**

## 4. Part 4 — the six safety questions, resolved as far as is honest

Each item is labelled with exactly what it is: **implemented**, **implemented + tested**, **proposed**, or **unresolved**.

### 4.1 The removable-label bypass — **CLOSED, implemented + tested**

The probe originally fell back to reading `relay-block*` labels when the entity store was unavailable. That is a bypass wearing a fallback's clothes: anyone with edit permission on the issue could delete the label and close the case.

- `createGateHandler()` no longer takes a label reader by default. `allowLabelFallback` is opt-in, and when used it emits `{"warning":"LABEL_BYPASS_ACTIVE"}` on every invocation.
- `index.js` passes `getLabels: undefined`. Gate state comes from the entity store and nowhere else.
- The UNBLOCK matrix now drives state through the webtrigger (`?action=state&key=…&blocking=2`) instead of labels.
- Test: *"F5: labels are NOT consulted by default, even when the store fails"* asserts the label reader is never called.

### 4.2 Authoritative enforcement state — **implemented + tested**

One record per project/unit, written only by the app, versioned with `updatedAt`, read by the validator. If the record is absent, malformed, or older than **15 minutes**, it is treated as *unavailable* — never as *clear*. `isStale()` and the resulting `unverified` stamping are covered by tests.

### 4.3 The four closure states — **implemented + tested**

`src/enforcement.js` derives exactly one of `verified | unverified | overridden | disabled` for every closure that actually happened, with strict precedence:

| Input | State | Reason |
| --- | --- | --- |
| valid override (actor + reason ≥ 20 chars) | `overridden` | `OVERRIDE_ACCEPTED` |
| Relay not enabled on the project | `disabled` | `RELAY_NOT_ENFORCING` |
| store unavailable | `unverified` | `GATE_STATE_UNAVAILABLE` |
| state older than 15 min | `unverified` | `GATE_STATE_STALE` |
| closed despite a block | `unverified` | `CLOSED_DESPITE_BLOCK` |
| gate evaluated and returned clear | `verified` | `GATE_EVALUATED_CLEAR` |
| no decision, unknown code, malformed audit | `unverified` | `NO_EVALUABLE_DECISION` |

The invariant the tests exist to protect: **no combination of inputs produces `verified` unless the gate actually evaluated and returned clear.** A short override reason does not count as an override. `countsAsCompliant()` is true for `verified` alone.

`complianceSummary()` excludes `disabled` closures from the denominator but still reports them, so a misconfigured project is visible rather than silently omitted. The generated headline can never be inflated by unverified or overridden closures — tested.

### 4.4 Fail-open versus fail-closed — **resolved by design, implemented + tested**

The two requirements were never actually in conflict once they were separated:

- **At the workflow:** fail **open**. If the store cannot be read, the transition proceeds. Relay must not be the reason a duty-of-care case cannot be closed during an outage.
- **In the record:** fail **loud**. That closure is stamped `unverified` and excluded from compliance.
- **Per project:** `fail-closed` is available and opt-in for tenants who prefer it (`resolvePolicy()` defaults to `fail-open`; tested).

So an infrastructure failure produces *a closure that is allowed but not counted as verified* — there is no state in which a closure is recorded as gate-checked when it was not.

What this does **not** fix is the platform's own behaviour when our function never runs at all (§3.4). That is not ours to configure, and it stays **unresolved** until T10.

### 4.5 The uninstall hazard and administrator recovery — **logic implemented + tested; transport missing; live behaviour UNRESOLVED**

`src/uninstall-audit.js` provides:

- `auditUninstall({workflows, appRuleKeys})` → `{safe, attachments[], summary, checklist[]}`. It refuses to say *safe* while any rule of ours is attached to any transition — validators, conditions **and** post functions, not just validators. 7 tests including "malformed input never produces a false safe".
- `RECOVERY_RUNBOOK` — six ordered steps for an admin whose transitions are blocked, **every step marked `verified: false`** and asserted as such by a test.

Two deliberate gaps:

1. **The transport is not implemented.** Enumerating a site's workflows and their attached rules needs a REST endpoint I could not verify from here. Writing it from memory would be inventing an API, which is the one thing this project keeps being told not to do. It is a ~20-line adapter behind `fetchWorkflows()` and it should be written against the real endpoint on a live site, in an hour, with the response shape open in front of you.
2. **The runbook is unexecuted.** It is the correct procedure as far as documentation goes — remove the orphaned rule, *publish the workflow*, verify with a test item. Until someone actually recovers a blocked workflow with it, it is a proposal.

**Hazard status: unresolved.** Mitigation: partially built.

### 4.6 Can an unavailable app leave a workflow unusable? — **UNRESOLVED**

Expected **yes**, on the strength of JRACLOUD-23885 and the general semantics of "a rule that does not evaluate true is not satisfied". Not confirmed. A "yes" here turns the uninstall checklist from good practice into a shipping requirement, and a "no" removes a P0 feature from the MVP. It is worth 10 minutes of T10 to find out.

## 10. Decision

### PROCEED AFTER FIXES — unchanged, and unable to advance

This is the same verdict as Phase 0 and it carries the same caveat, because the evidence base is the same for the two questions that matter. Five of the seven fixes moved; neither of the two blocking ones did.

- **Not PROCEED:** the gate has still never blocked a transition, and the extraction has still never been measured. Phase 0.2 added no live evidence for either.
- **Not PIVOT:** the pivot criterion is "precision below 60% after two iterations". No precision has been measured, so the criterion has not been triggered. Pivoting would be a decision made from discomfort rather than data.
- **PROCEED AFTER FIXES:** F1 and F2 remain the gate. They are not blocked by a technical unknown anymore — they are blocked by an account and a site, which is the cheapest blocker this project will ever face.

**Standing rule, unchanged:** no product code until T9 passes and the benchmark has numbers. If T9 fails, the enforcement thesis needs rewriting before anything else. If precision lands under 60% twice, pivot to Close Call using the shared Phase 1–2 work.

Phase 0.2 did its job in the narrow sense: it did not let a validated-looking document stand in for an unvalidated system.
