# P2.2 — Management lifecycle, conditional commits, append-only audit

**Status:** implemented and tested locally (177/177 tests, `tsc`, `check:render`,
`vite build`, `check:manifest` — 17 checks, including the manifest schema Forge
ships). **Not deployed, not linted, not verified on a live site** — this sandbox
cannot reach Forge (`forge deploy` / `install` / `lint` need an Atlassian login,
see §9), and it cannot run a browser (§8). Everything below that touches
Atlassian is a runbook, not a result. §12 lists the manifest defects P2.2 shipped
with, all fixed in P2.2.1.

---

## 1. What P2.2 changes, in one paragraph

P2.1 could answer *"how many promises are open?"* but not *"does Relay manage
this issue at all?"*. A single number cannot express that: zero would permit a
case Relay has never seen, which is the fail-open the brief forbids. P2.2 adds a
second app-owned field (**management state**: `managed`, `initializing`,
`unmanaged`), makes the workflow condition read both, replaces the advisory lock
with a **conditional commit on the record's revision**, makes the audit trail
**append-only** (one key per event), and adds the lifecycle that moves an issue
between states — track, untrack, backfill, and an issue-created trigger.

---

## 2. The closure contract (the table to test on the site)

| Record state | Count field | Validator (agent/REST) | Condition (portal) |
| --- | --- | --- | --- |
| `unmanaged` | anything | **permit** | **permit** (first branch short-circuits) |
| `managed` | `0` | permit | permit |
| `managed` | `> 0` | block, with a message naming the work | withhold |
| `managed` | `null` | block (never coerced to 0) | withhold |
| `managed` | non-numeric | block | withhold |
| `initializing` | anything | block — "still initialising" | withhold |
| **no record** | anything | **block** — "no management state" | withhold (expression error: field is untouched/absent, or state is empty) |
| record state unrecognised | anything | block | withhold |

The expression in the manifest is exactly:

```
(issue.<stateField> == "unmanaged") || (issue.<stateField> == "managed" && issue.<countField> == 0)
```

`missing` is never read as `unmanaged`. Both paths ask one function
(`decideClosure`, `src/gate.js`); the expression is mirrored by
`evaluateClosureCondition` (`src/field.js`) and the mirror is tested against the
decision for every state (`test/p2-2.test.js`, check 12).

## 3. Where the record lives, and why

`app.storage.entities` in `manifest.yml` declares one Custom Entity Store
entity, `relay-ledger`, keyed by issue key:

| attribute | type | purpose |
| --- | --- | --- |
| `issueKey` | string | the key, also the entity key |
| `rev` | integer | **the revision every commit is conditioned on** |
| `version` | integer | record format version |
| `state` | string | `managed` / `initializing` / `unmanaged` |
| `digest` | string | content digest of the commitment list |
| `updatedAt` | string | ISO timestamp of the last commit |
| `commitments` | any | the commitment array (see `ledger.js`) |

Writes go through `src/store.js` and are committed by `src/forge-store.js`:

```js
kvs.transact()
  .set(issueKey, next, {
    entityName: 'relay-ledger',
    conditions: new Filter().and('rev', FilterConditions.equalTo(expectedRev)),
  })
  .execute();
```

A commit that lost the race fails the condition; `mutateLedger` re-reads, re-runs
the mutation against what actually exists, and retries (5 attempts, jittered
backoff). The **advisory lock is gone** — P2.1 also ran the mutation when the
lock was not acquired, which is why the lock was never a guarantee.

Creates are `keyPolicy: 'FAIL_IF_EXISTS'` (`kvs.entity('relay-ledger').set`), so
two simultaneous Track clicks — or the trigger racing the backfill — produce one
record and the loser adopts it.

**Why an entity and not a key:** Forge KVS has no compare-and-swap. The entity
store is the only Forge storage that offers a conditional write and a
create-only write.

## 4. The management lifecycle

### Track (`relay.workspace.track`)

1. create the record (create-only) in `initializing`;
2. write the **state field** `initializing` and read it back;
3. commit the record `initializing`;
4. capture the issue's comments into the ledger (idempotent by evidence fingerprint);
5. project the count and state, **verify both**;
6. commit `managed`, then write the field `managed`, **verify it**;
7. bring the projection back into step with the final revision.

A failure at any step leaves the issue `initializing` — withheld on both paths —
and returns `{ status: 'failed', stage, steps }` so the console can say where it
stopped. `capture` failing (comments unreadable) is the named
"extraction unavailable" case.

Re-running Track on a managed issue is a **refresh**: it re-verifies the fields
and captures nothing twice (`status: 'already_managed'`).

### Untrack (`relay.workspace.untrack`)

Requires `confirm: true`. Without it the handler returns
`confirmation_required` with the number of unresolved commitments that will be
left behind, and changes nothing. With it:

1. state field → `initializing`, verified;
2. record → `initializing`;
3. record → `unmanaged` (ledger **kept** as evidence);
4. state field → `unmanaged`, verified;
5. remove from the tracked list; append `untracked` to the audit trail.

Passing through `initializing` on both sides is what makes a half-finished
offboarding *withheld* rather than open.

### Backfill (`relay.workspace.init`)

Pages a JQL search (`project = "FS" ORDER BY key ASC`) and records every issue
as `unmanaged`, one page at a time (`max` ≤ 100, default 25). It is resumable by
`nextPageToken`, **skips** issues that already have a record, and never
overwrites one — so running it while the app is live cannot unmanage a case.

### Trigger (`onIssueCreated`)

`avi:jira:created:issue` runs the same `relay.state.init` handler the backfill
uses, so every new issue has a record at creation instead of waiting for
someone to open it.

## 5. The audit trail

One key per event: `relay:audit:{issueKey}:{eventId}`, written
`keyPolicy: 'FAIL_IF_EXISTS'` and read back.

* The event id is deterministic (`type:issue:commitment:rev`), so a retried
  queue message or a double click is a **duplicate**, reported and not
  re-recorded.
* Two writers appending at the same time **both** succeed — P2.1's
  read-whole-array/write-back lost one of them silently.
* Reads are paginated by prefix with a cursor (`store.readAudit(key, { limit,
  cursor })`), so a long trail is read rather than truncated; `truncated` is
  reported.

Retention: events are never deleted by Relay. They count towards `storage:app`.

## 6. Deployment order (do not reorder steps 4–6)

1. **Build and deploy** (`npm run forge:deploy`). Forge creates both field
   instances; Jira assigns `customfield_NNNNN` ids.
2. **Resolve the ids**: open Relay → Settings → Enforcement → *Fields*. Relay
   caches both ids in `relay:settings` with the environment's type ids.
3. **Copy the printed `manifestLine`** into `manifest.yml` under
   `jira:workflowCondition.expression`, replacing the placeholder, and deploy
   again. Record it in Settings ("record the expression") so
   `relay.enforcement.check` stops warning.
4. **Backfill before attaching the condition**: Settings → *Backfill the
   project*, repeatedly until it reports complete.
5. **Verify coverage**: Settings → *Reconcile*. `report.noLedger`,
   `report.initializing`, `report.failed` and `report.inaccessible` must be
   empty. A tracked issue with no record is a failure, not a success.
6. **Attach the validator and the condition** to the closure transition on the
   site (Relay cannot do this from inside an app), then record that you did in
   Settings so the console stops saying "unverified".
7. **Spot-check** one case per state with Settings → *Run check*: it reports the
   record state, the validator's decision, the projection, the count field and
   the state field — and names any disagreement.

Order matters because the condition is fail-closed: between step 3 and step 4
every issue without a record is refused, for everyone.

## 10. Rollback

* **Stop the bleeding (portal):** detach the condition from the closure
  transition. Relay cannot detach it for you; this is a site edit.
* **Stop the bleeding (agents):** remove the validator from the transition, or
  set the record state to `initializing` for the affected issues (Track does
  this automatically on failure).
* **Data:** records are additive. To take an issue out of Relay's way without
  deleting evidence, `untrack` it (confirming) — the ledger and trail remain.
* **Code:** P2.2 is one commit; `git revert` it. The entity and the second field
  remain declared in the old manifest only if you also revert the manifest, and
  Forge will refuse to *delete* a deployed entity attribute — revert the code
  first, leave the entity in place.

## 12. Manifest corrections in P2.2.1

The manifest P2.2 shipped was not deployable, and every check that existed at the
time passed it. Four defects, in the order a deploy would have hit them:

| # | Defect | Symptom | Fix |
| --- | --- | --- | --- |
| 1 | two `description:` scalars contained an unquoted `: ` (`projection: the number…`, `— managed, initializing or unmanaged`) | YAML parse error: *Nested mappings are not allowed in compact mappings* — a Windows checkout reported it first because the parser is the same everywhere, the reporting is not | both descriptions are double-quoted scalars |
| 2 | neither `jira:customField` declared a `resolver` | the field module is invalid: the manifest reference marks `resolver` required for every `jira:customField` | `resolver: { function: relay-resolver }` on both |
| 3 | `jira:issuePanel` had no `icon` | the module is invalid: `icon` is required, and it may be a path inside a declared resource | `icon: icon.svg`, and the file ships in `ui/public/` so vite copies it into `static/relay` |
| 4 | `function:` was a top-level section | the manifest schema has `additionalProperties: false` at the root and no `function` key | functions moved to `modules.function`, which is where the module reference documents them |

### 12.1 The resolver, precisely

`relay-resolver` → `index.handler` already existed; nothing was added to the
code. What the manifest now says is that each read-only field points at that
resolver, because Forge requires the property on the module — a `jira:customField`
without one is rejected before the field is created.

The fields are still `readOnly: true` with **no** `view`, `edit`, `value` or
`function` surface: Jira renders them natively and Relay writes them through
`PUT /rest/api/3/app/field/{fieldIdOrKey}/value`. So nothing in the console's
resolver map is registered for these fields, and no handler was invented to
"serve" them. Whether Jira ever invokes the resolver for a read-only field with
no rendering entry point is **not verified** — it cannot be, without a deploy.
If it does, the invocation reaches the same resolver map the console uses and
returns `unknown_resolver`; that is a log line, not a broken field.

### 12.2 Why the old gate passed all four

`check:manifest` was hand-written and line-oriented: it matched `key:`,
`handler:`, `type:` with regexes and never parsed the file, so a scalar that
swallows the next four lines looked fine. It also only checked the attributes it
remembered (name, type, readOnly) and never compared the document to Forge's own
schema. Two of the four defects were invisible to it by construction.

It now: parses with `yaml` (`uniqueKeys`, so duplicate keys fail), checks shapes
per module type against the attributes those modules actually accept, resolves
every function/resource reference and confirms the handler is a real export of
the file it names, compares the entity to `RECORD_ENTITY` in `src/forge-store.js`,
checks the closure expression's semantics, and finally hands the file to
`@forge/manifest@13.8.0` — 17 checks, and it fails the four manifests above.

### 12.3 What is still not verified

* `forge lint` has not run (needs a login; see §9). The schema half of it now
  runs offline; its rule half does not.
* No deploy, no install, no site. Field creation, the private app-field write,
  the condition and the validator are all unchanged by this correction — but they
  remain unexercised against Atlassian since P2.1.
* `resolver` semantics for a read-only field with no UI, as above.

## 13. P2.2.2 — the 422 on `entity.set()`

### 13.1 What failed

The first Track after the P2.2 deploy returned `HTTP 422 UNPROCESSABLE_ENTITY`
from `src/forge-store.js` (`entity.set()` inside `records.create`). Three defects,
all in the same write:

| # | Defect | Store rule |
| --- | --- | --- |
| 1 | the record carried `source` and `trackedBy`, attributes the entity did not declare | an entity accepts only declared attributes; adding one is a manifest change |
| 2 | the record carried `null`: `trackedBy`, and inside every commitment `owner`, `dueAt`, `acceptedBy`, `verificationNote`, `droppedAt`, `droppedReason`, `suggestedOwner`, `verifiedAt`, `verifiedBy`, and `commentCreatedAt`/`bodyHash`/`author.id` in `evidence` | `null` is not a value of any type, `any` included; `""` is rejected as well (`string` must contain a non-whitespace character) |
| 3 | the created record had no `digest` (`emptyLedger()` did not set one) | a declared attribute that is written must match its type; a missing one cannot be verified |

### 13.2 The fix, and why it is where it is

`src/record-codec.js` is the only code that knows what an entity can hold:

* `toStored(record)` keeps only declared attributes — tested with
  `Object.hasOwn`, not `RECORD_ATTRIBUTES[name]`, because the latter walks the
  prototype chain and would accept `toString` or `constructor` as an attribute —
  and **omits** any value that is `null`, `undefined` or `""`, recursing through
  objects and arrays so nested optionals (and nested people, whose `id` is the
  nullable part) go too. Objects are assembled with `Object.fromEntries`, so a
  `__proto__` key is a data property (and then rejected as undeclared) instead of
  a prototype write;
* `fromStored(value)` restores the nulls from an explicit list of nullable keys,
  so a commitment read back is the shape it was written in — `owner: null`, not
  `undefined`;
* a record that cannot be stored throws `RecordShapeError` naming the attribute
  *before* the network call — an undeclared attribute, a non-finite number, a
  `Date`, a null array element (positional, so dropping it would change meaning),
  or a missing required attribute.

### 13.2.1 Reading: forward compatible, and strict about what it trusts

`fromStored` has two policies, and they are deliberately different:

* **Unknown attributes survive a read.** An attribute this build does not know
  about is kept verbatim, so a record written by a newer build is never emptied
  by an older one. It is *not* carried into a write: `toStored` refuses it,
  naming it, because the entity does not declare it. A record like that can be
  read by this build and not rewritten by it — loud, and no data lost silently.
* **Core ledger state is required, never defaulted.** `issueKey`, `rev`,
  `version`, `state`, `commitments` and `updatedAt` must be present and sane;
  anything else throws `RecordShapeError` naming the field. A substituted `rev`
  would make the conditional write compare against a revision nobody wrote, and a
  substituted empty `commitments` list would read as *nothing open* and permit
  closure — the fail-open this whole module exists to prevent. `state` must be
  one of the three management states; an unrecognised string is corrupt, and
  guessing which state was meant changes whether a case can be closed.

* **A commitment status outside the four is refused.** `isUnresolved()` is
  `status === 'open' || status === 'proposed'`, and that number is what the
  closure contract reads — so anything it does not recognise is classified as
  *settled* and silently drops out of the open count. A commitment whose status
  is missing, empty, or not exactly `proposed`/`open`/`verified`/`dropped`
  therefore throws at `commitments[n].status`, naming its position. The four are
  the only values any version of this codebase has written: `toRecord()` creates
  `proposed`, `relay.capture.accept` sets `open`, `relay.commitment.verify` sets
  `verified`, `relay.capture.reject` sets `dropped`.
* **A stored digest is verified, not carried.** When a digest is present it is
  recomputed from the stored commitments and compared; a mismatch throws at
  `digest` and is never repaired. The mismatch is the only evidence that a
  record does not describe its own contents — after a partial write, a hand edit,
  or a writer that digested different fields — and recomputing it would destroy
  that evidence.

Both rules also run on the way **in**: `toStored` validates the commitments it is
about to write (statuses, shape, and that the digest describes them). A record
that is stored but cannot be read back is worse than a local error — it fails
closed on every later read and withholds closure for that issue until someone
untracks and re-tracks it — so a writer bug is refused before the network call,
with nothing stored.

The **only** legacy allowance is the digest: a record created by the pre-P2.2.2
path has none (that is the bug), so one is derived from the content it does have.
A digest that is present but unusable (`null`, `""`, a number) is corrupt and is
refused — the repair is for an absence, not a bad value.

The consequence for an operator: a corrupt record cannot be repaired by Relay,
because Relay will not guess at it. It has to be removed and recreated
(untrack/backfill a fresh record) on the site. That is a deliberate trade: an
unreadable record blocks closure, a fabricated one would permit it.

The omission is deliberate and it is not a default: nothing is invented. In this
domain "the key is absent" and "the value is null" are the same statement — *not
recorded* — and the store has no null to put there. An empty string is treated
the same way; every consumer already treats `""` and `null` alike (`note || null`,
`c.verificationNote ?? ''`).

`emptyLedger()` now carries `digestOf([])` (`0:811c9dc5`), and `initialise()`
verifies **revision, state and digest** of the record it reads back — a create
that returns is still a claim.

The fake record store in `test/support/fake-forge.js` now stores the *encoded*
record and enforces the service's value rules independently of the codec. If the
codec ever stops stripping something, the suite fails with the service's
complaint instead of passing against a fake that accepts anything.

`npm run check:manifest` compares the declared attributes with
`RECORD_ATTRIBUTES` in both directions: an attribute the code writes but the
entity does not declare is a failure (that is defect 1), and a declared
attribute whose type disagrees is a failure too.

### 13.2.2 What the digest covers, and what it deliberately does not

`digestOf()` hashes, per commitment: `code`, `status`, the owner's identity
(`id`, or `name` when there is no account id), `dueAt` and `text`. It hashes the
sorted list, so ordering does not move it, and prefixes the count
(`0:811c9dc5` for an empty ledger).

| Covered | Not covered |
| --- | --- |
| `code`, `status`, owner identity, `dueAt`, `text` | `originalText`, the whole `evidence` chain (`commentId`, `commentCreatedAt`, `body`, `bodyHash`, `bodyFormat`, `quote`, `start`, `end`, `author`, `fingerprint`, `capturedAt`), `confidence`, `signals`, `suggestedOwner`, `dueBasis`, `acceptedAt`, `acceptedBy`, `verifiedAt`, `verifiedBy`, `verificationNote`, `droppedAt`, `droppedReason`, `previousOwners` |

That is the fields Relay *decides* from (`isUnresolved`, `counts`, the closure
contract) plus the wording a person accepted. It is a **same-revision
consistency check, not tamper evidence**: FNV-1a is 32 bits, unseeded and not
collision resistant, so it cannot be a security boundary whatever it hashes; the
guard against a rival write is the revision in the conditional write, and the
digest answers a narrower question — *did the record read back hold the
commitments I just wrote?* The quotation is anchored where it belongs:
`evidence.fingerprint` covers issue, comment, offsets and the quote, and
`evidence.bodyHash` covers the comment body, both re-derived from Jira when the
comment is rescanned.

**The algorithm is frozen for a compatibility reason.** `fromStored` verifies the
stored digest against the stored commitments, so widening what it hashes would
make every record already in the entity store fail its own check and be refused
— every tracked issue would stop reading, and closure would be withheld
project-wide until each record was rewritten. A wider digest therefore has to
arrive as a versioned algorithm (`v2:` prefix, both versions verifiable on read),
and that is a change to make when the guarantee is restated as *record-wide
integrity* — not as a quiet improvement. A test asserts the boundary in both
directions: changing `text`, `code`, `status`, owner identity or `dueAt` breaks
the digest; changing `evidence` or `verificationNote` does not.

### 13.2.3 A 422 that says nothing, and what Relay now keeps

The first Track on a live site still dies on the first ledger write:

```
ForgeKvsAPIError: Request cannot be processed due to one or more semantic errors
HTTP 422   POST /api/v1/entity/set
  at StorageApi.setEntity (@forge/kvs/out/storage-api.js)
  at create (src/forge-store.js)
  at initialise (src/store.js)  ← handlers.trackIssue
```

That sentence is the service's `message`. `@forge/kvs` builds `ForgeKvsAPIError`
from the response body `{ code, message, ...context }` and keeps `code`, a
`responseDetails` object (status, status text, trace id, path) and `context` as
separate fields — but every caller in Relay read `err.message` only, so the
platform's own code was discarded at the throw site. An error that carries a
code could be attributed; the sentence alone cannot.

`src/forge-store.js` now re-wraps a platform failure on `create`/`update` as
`StorageRejected` and keeps `platformCode`, `status`, `traceId`, `operation`,
`entityName` and the attributes that were sent — names and declared types only,
never values, because a record holds comment text. It travels as `track.error`
and in the `track_failed` log line, so the next Track on a live site prints the
platform's own answer instead of the sentence alone. `RecordExists`,
`RevisionConflict` and network errors are unchanged: a conflict is still a
conflict, and `fetch failed` is still `fetch failed`.

Three details of that wrapper matter when reading a live 422:

* **`code UNKNOWN_ERROR` is the client's own fallback, not a missing field.**
  `@forge/kvs` throws `{ code: 'UNKNOWN_ERROR', message: 'Unexpected error in
  Forge KVS API', context: { responseText } }` when the response body is not a
  `{ code, message }` object (`out/utils/error-handling.js`). So a 422 whose body
  is HTML or a bare array looks exactly like an unknown error, and its text is in
  `context.responseText`. If instead the body *is* a `{ code, message }` object,
  every other key of the body is folded into `context` by
  `ForgeKvsAPIError`'s constructor.
* **The context is printed as a shape, never as text.** Because `context` can
  hold the raw body — and the body can echo what was submitted — the message
  reports keys, types, array and string *lengths* (`body {code:string(22),
  errors:array(1)}`), plus the value of a naming key when the service sends one
  (`property=updatedAt`, `expected=string`). No record text can pass through.
* **Only the platform's own error is re-wrapped.** The check is
  `name === 'ForgeKvsError'` (or a `responseDetails` object), not "has a string
  `code`", so a Node transport error (`ECONNRESET`, `EAI_AGAIN`) is not
  relabelled as a store rejection.

Where the details surface matters as much as keeping them. At first the record
create sat *before* `trackIssue`'s fail-closed `try`, so a refusal on the first
write escaped the handler: no `track_failed` line was logged and the console fell
through to a generic error toast. It now sits inside the block, `hasRecord`
decides whether there is a state to restore, the failure is logged with
`stage`, `platformCode`, `httpStatus` and `traceId`, and the console's failed
Track toast prints `track.error` next to the stage. The stage for a refused
create is `record_initialise`.

**What the offline evidence rules out, and what it cannot.** The payload for an
initial Track is eight attributes — `version`, `rev`, `issueKey`, `state`,
`commitments` (`[]`), `digest`, `updatedAt`, `source` — every one declared in
the local manifest, every value matching its declared type (`any` accepts
`array`; `integer` is int32; every string is non-empty). A *wrong-typed* value
on a direct `entity.set` is reported as `400 INCORRECT_PROPERTY_TYPE` naming the
property, so a bare 422 is not the value layer. Since `entity.get` succeeds
before the write, the entity exists in that environment — so the rejection is
about the attribute set or about a name, not about the entity, the key, the
scope or `keyPolicy: 'FAIL_IF_EXISTS'` (all documented and all exercised here).

Three candidates remain, and none is decidable from this repository:

1. **The deployed entity does not declare one of the written attributes.** The
   manifest changes cannot be backported (`forge deploy --major-version` ignores
   `app.storage`), and a local edit is not a deployment. `digest` is the newest
   attribute, so it is the first to check.
2. **An attribute name is reserved by the service.** Of the eight, `updatedAt`
   is the only one that matches a Forge-managed metadata field name
   (`createdAt` / `updatedAt` / `expireTime`, also `MetadataField` in
   `@forge/kvs`). `@forge/manifest`'s own storage validator checks counts, name
   length, name pattern and index rules — never reserved names — so neither
   `check:manifest` nor `forge lint` would catch this.
3. **The store requires every declared attribute to be present.** Relay omits
   absent optional attributes deliberately (no placeholder values); the 13
   declared attributes are not all written on a create.

**The deployed attribute set cannot be listed by any Forge CLI command.** The
only storage command is `forge storage entities indexes list -e <environment>
[--json]`: it returns entity names and their indexes (`name`, `partition`,
`range`, `status`) and no attributes at all — its GraphQL query asks for
`name`, `status` and `indexes { name partition range status }` and nothing else
(`@forge/cli` 14.2.0, `out/entities/graphql-client.js`). It also needs a login.
There is no `forge storage entities list`; that command does not exist.

So the live schema can be settled in exactly two ways, both of which need the
logged-in machine and both of which change something:

```bash
# 1. index state only — proves the entity and its indexes exist, not its attributes
npx @forge/cli storage entities indexes list -e development --json
```

```bash
# 2. the only command that reports the deployed attributes: a deploy whose
#    manifest removes or retypes one of them is rejected, and the rejection
#    names it. This is a mutation and needs explicit approval.
npx @forge/cli deploy -e development
```

Otherwise, click Track once and read the new error: `platformCode` names the
reason (`INVALID_ENTITY_ATTRIBUTE`, `INVALID_ENTITY_VALUE`, …), `traceId` goes
to Atlassian support verbatim, and `attributes` lists what was sent.

That answer is read against the three candidates above, not guessed at:

* a code naming an attribute the local manifest already declares rules out
  candidate 1 (the deployed entity is missing nothing) and points at
  candidate 2 — a name the service itself reserves or restricts;
* a complaint about a *missing* attribute is candidate 3, and its repair is a
  design decision about placeholder values, not a patch;
* `UNKNOWN_ERROR` means the body was not a `{ code, message }` object at all,
  so the trace id is the only route forward.

Candidate 1 is confirmed only by a deploy that reports the deployed attributes,
and its repair is a deploy of the manifest rather than a code change. It must
never be worked around by dropping `digest` from the write, which would remove
the integrity check this record depends on.

### 13.3 The assumption that needs a live check

Omitting a declared-but-unset attribute is accepted by the store — that is the
one thing this cannot prove offline, and the alternative (writing a placeholder
`"unknown"` for an absent account id) would be a fabricated value. If the deploy
still returns 422 on a Track, read the error's `code`/`message`:

* `INVALID_ENTITY_VALUE` naming an attribute → the codec missed a value; report
  the attribute and the operation, it is a one-line fix in `sanitise`.
* an error about a **missing** attribute → the store requires every declared
  attribute; the fix is to give the six lifecycle attributes placeholder values
  at create and stop treating omission as legal, which changes the design
  described in §13.2 rather than patching around it.
