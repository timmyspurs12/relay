# The first ledger write and its 422 — decision report

**Status:** offline. Nothing here was deployed, installed or run against the live
site; no live call was made from this workspace. Uncommitted change, no push.
**Subject:** `POST /api/v1/entity/set` for entity `relay-ledger` returning
`422 Request cannot be processed due to one or more semantic errors` on the first
Track.

## Decision

**Diagnostic instrumentation only. The root cause is not confirmed.**

No manifest change, no schema deployment, no code that dodges the rejection. The
work in this change makes the next live Track *attributable*: it keeps the
platform's `code`, HTTP status and trace id, reports the attribute set that was
sent (names and types only), puts both in the log and on the console, and stops
printing a response body that could contain a record's text. The three surviving
hypotheses are unchanged and none is decidable from this repository — see
[What is documented and what is inferred](#3-documented-fact-versus-inference).

Why not the alternatives:

* **Not a schema deployment requirement yet.** It would be the right repair if
  hypothesis 1 held (the deployed entity is missing a written attribute), but
  that is exactly what cannot be observed from here — a deploy is a mutation, and
  the CLI cannot list attributes (see [1](#1-can-the-deployed-attribute-set-be-listed)).
  Guessing it would mean re-deploying a manifest that is already correct and
  calling the 422 "fixed" if it disappeared for an unrelated reason.
* **Not a specific code repair.** The value/type layer is ruled out by the
  published contract and by what the codec writes; there is no attribute-value
  defect to fix. Any repair now would be a workaround (drop `digest`, rename
  `updatedAt`, write placeholder values) — each removes a real property of the
  ledger to silence an error nobody has read yet.

## 1. Can the deployed attribute set be listed?

**No. Not by this workspace, and not by any Forge CLI command.**

Verified against an installed CLI, not from memory: `@forge/cli@15.0.0` refuses
this sandbox's Node (v22.22.3; it wants `^22.23.4 || ^24.22.1 || >=26.12.1`), so
`@forge/cli@14.2.0` was installed in `/tmp/forgecli`. Its own help gives the only
storage surface:

```
forge storage entities indexes list [-e <environment>] [--json]
```

and the implementation confirms what it returns: `getEntitiesDefinitions()`
issues a GraphQL query for `name`, `status` and
`indexes { name partition range status }` — **no attributes**
(`out/entities/graphql-client.js`, `out/service/custom-entities-service.js`). The
command also needs an Atlassian login, which this workspace does not have. There
is no `forge storage entities list`; that command does not exist, and an earlier
draft of `docs/P2.2-RUNBOOK.md` §13.2.3 named it — corrected there.

Consequently **the attribute-by-attribute comparison against the live
`relay-ledger` cannot be produced.** The local manifest declares 13 attributes:
`version:integer`, `rev:integer`, `issueKey:string`, `state:string`,
`commitments:any`, `digest:string`, `updatedAt:string`, `source:string`,
`trackedBy:string`, `trackedAt:string`, `untrackedAt:string`,
`untrackReason:string`, `backfilledAt:string`. Whether the deployed entity
declares all 13 is unknown.

Two things a person with the login can do — both are mutations or near-mutations
and need explicit approval:

| Action | What it proves | Cost |
| --- | --- | --- |
| `forge storage entities indexes list -e development --json` | the entity exists and its indexes' status — **nothing about attributes** | login only |
| `forge deploy -e development` after temporarily removing one attribute from the manifest | the deploy is rejected and the error names the attribute ⇒ it is deployed; accepted ⇒ it is not | a deploy; must not be left in that state |

## 2. Does the create path go through the injected client?

**Yes — and this is now proven by a test rather than by reading.**

`createForgeRecords(client = kvs)` binds `const entity = client.entity(RECORD_ENTITY)`
once, and `create` calls that `entity.set`; `update` calls `client.transact()`.
The original concern (that a passing suite might be exercising the module-level
`@forge/kvs` binding instead of the fake) is settled empirically: outside Forge,
the real binding fails with

```
TypeError: global.__forge_fetch__ is not a function
```

(measured in this sandbox against the installed `@forge/kvs@2.1.1`). The new
test `the create path talks to the client it is handed, not the module binding`
hands `createForgeRecords` a client whose `entity(name)` asserts
`name === 'relay-ledger'` and whose `set` throws a sentinel, then asserts the
sentinel is what surfaces. A module-level implementation could not produce it.

The wrapper's own tests were also checked for faithfulness: the first test's
`assert.equal(sent.length, 1)` records the arguments the *fake* `set` received,
which is only possible if the fake is on the path.

## 3. Does the wrapper keep the platform's details, leak nothing, and reach a human?

What is kept and where it goes:

| Field | Source | Reaches |
| --- | --- | --- |
| `platformCode` | `cause.code` | message, `track.error`, `track_failed` log, `track.platformCode` |
| HTTP `status` | `cause.responseDetails.status` | same |
| `traceId` | `cause.responseDetails.traceId` (`x-b3-traceid` / `x-trace-id`) | same |
| `operation`, `entityName`, `issueKey` | Relay | same |
| `attributes` | the encoded record | message as `name:type`, and `err.attributes` |
| service sentence | `cause.message` | message |

`code` is **not** assumed to be `UNKNOWN_ERROR`. It is whatever the platform
sent, and `UNKNOWN_ERROR` has a specific, verifiable meaning: `@forge/kvs` uses
it when the response body is not a `{ code, message }` object, in which case it
also stores the raw body in `context.responseText`
(`out/utils/error-handling.js`). A 422 body that is HTML or a bare array
therefore *looks* unknown while its text sits in `context`.

That is why the context is no longer dumped. `ForgeKvsAPIError`'s constructor
merges every non-`code`/`message`/`context` key of the body into `context`, so
`context` is untrusted server JSON that can echo what was submitted — and a
record contains comment text and people's names. The message now reports the
context's **shape**: key names, value types, array and string lengths, plus the
value of a naming key (`property`, `attribute`, `field`, `expected`, `type`,
`path`) which is the one datum that identifies an offending attribute. Verified
by tests: a body containing `"comment": "Can you send the certificate…"` produces
`body {code:string(22),message:string(41),comment:string(32)}` and no record
text.

Re-wrapping is also narrowed to the platform's own error class
(`name === 'ForgeKvsError'` or a `responseDetails` object). Testing "has a string
`code`" matched Node system errors, which would have relabelled an `ECONNRESET`
as a store rejection.

Surfacing, end to end (this was broken and is now fixed):

* the record create used to sit **before** `trackIssue`'s fail-closed `try`, so a
  refusal on the first write escaped the handler — no `track_failed` log line,
  no structured result, and the console fell through to its generic toast;
* it is now inside the block (`hasRecord` decides whether a state has to be
  restored), the failure is logged with `stage`, `platformCode`, `httpStatus` and
  `traceId`, and returned as `track.stage` / `track.error` with stage
  `record_initialise`;
* `app/ui/src/App.tsx` printed the stage but **never** `track.error`; it now
  appends it to the failed-Track toast, so the platform's answer is on screen
  without opening the Forge logs.

## 4. The three hypotheses

**H1 — the deployed entity is missing a written attribute.** Not excluded. The
create writes 8 of the 13 declared attributes; `digest` is the newest, and
manifest changes inside `app.storage` cannot be backported
(`forge deploy --major-version` ignores the `storage` block). Nothing offline can
distinguish "deployed without `digest`" from "deployed with it".

**H2 — an attribute name is reserved by the service.** Not excluded, and no
longer supported by any evidence I can find. The only plausible candidate was
`updatedAt`, because it matches Forge's managed metadata names (`createdAt`,
`updatedAt`, `expireTime`, `MetadataField` in `@forge/kvs`). But:
`@forge/manifest`'s storage validator checks counts, name length, name pattern
and index rules and never reserved names, so neither `check:manifest` nor
`forge lint` would report it — and the reference docs publish no reserved-name
list, while the documented `INVALID_ENTITY_ATTRIBUTE` cause is "attribute name is
a reserved value". Three public Forge apps declare `updatedAt` as an ordinary
entity attribute, two of them index on it
(`dhruvinhet/Quality-Loop`, `wjkennedy/A9-PMO-Screensaver`,
`mecvillarina/clair`). That is weak evidence — the apps' live state is unknown —
so H2 stays open, but `updatedAt` is not special enough to rename on a guess, and
renaming it would be a breaking manifest change for a hypothesis.

**H3 — the store requires every declared attribute to be present.** Not excluded,
and weakened: the docs state type rules, size and count limits and the deletion
rule, and say nothing about required attributes; and a public Forge app writes a
`decision` entity that declares 14 attributes with a 7-attribute first write
(8 when its optional `reasonCategory` applies) and adds the remaining
task-linking attributes later (`dhruvinhet/Quality-Loop`, `src/resolvers/decisionStore.js`
against its `manifest.yml`). If H3 were true that pattern would fail for everyone
who uses it. Note the constraint this creates: if H3 *does* hold, the repair is a
design change (placeholder values for the six unset lifecycle attributes), not a
patch — and it must not be reached by writing fabricated values silently.

## 5. Documented fact versus inference

| Claim | Status | Evidence |
| --- | --- | --- |
| The only storage CLI command is `storage entities indexes list`; it lists no attributes | documented + read from the CLI's own code | CLI 14.2.0 help; `out/entities/graphql-client.js`; docs page §"Deploying apps with indexes" |
| A 422 is not part of the published entity-set contract | documented | OpenAPI `swagger.v3.json`: `/v1/entity/set` responses are 200/204, 400, 409 |
| `UNKNOWN_ERROR` is the client's fallback for a non-`{code,message}` body, which is then kept in `context.responseText` | documented + read from source | `@forge/kvs@2.1.1` `out/utils/error-handling.js` |
| `ForgeKvsAPIError.context` merges all other body keys | read from source | `out/errors.js` constructor |
| `updatedAt` is a reserved attribute name | **not documented, not evidenced** | no reserved-name list in the reference docs; counter-examples above |
| The store requires all declared attributes | **not documented, not evidenced** | attribute type/size rules only; counter-example above |
| The deployed `relay-ledger` matches the local manifest | **unknown** | cannot be listed; needs a login and a deploy |
| The live 422 is caused by H1, H2 or H3 | **unknown** | no access to the response body or the deployed schema |

## 6. The proposed change (uncommitted)

`app/src/forge-store.js`
* context summarised by shape, naming keys only (`describeContext`, `shapeOf`);
* `isPlatformApiError` keyed on the platform error class, not on "has a `code`";
* `code` taken as sent, with the fallback documented.

`app/src/handlers.js`
* the record create moves inside `trackIssue`'s fail-closed block; `hasRecord`
  gates the state restore; the failure is logged with `stage`, `platformCode`,
  `httpStatus`, `traceId` and returned with them; stage `record_initialise` for a
  refused create.

`app/ui/src/App.tsx`, `app/ui/src/lib/api.ts`
* the failed-Track toast prints `track.error`; `TrackResult` gains
  `platformCode`, `httpStatus`, `traceId`.

`app/test/storage-rejected.test.js`
* new: injected-client routing proof; context shape redaction (two tests); a
  Node error code is not a store rejection; the end-to-end handler test (failed
  Track with stage/code/trace, one attempt, nothing persisted, no spurious
  restore, `track_failed` log).

`docs/P2.2-RUNBOOK.md` §13.2.3 — the non-existent command removed, the verified
CLI surface and the two approval-gated options written down, the surfacing change
described.

## 7. What would settle it, in order of cost

1. Open the console on the live site and press Track once. Read
   `track.stage`, `track.platformCode`, `track.traceId` and the attribute list in
   the toast — or the `track_failed` line in `forge logs`.
2. If `platformCode` is `UNKNOWN_ERROR`, the body was not a `{code,message}`
   object; the shape line says whether it was HTML or JSON, and the trace id goes
   to Atlassian support verbatim.
3. If the code names an attribute, compare that name with the local manifest: a
   mismatch is H1 and the repair is a deploy; a match is H2 and the repair is a
   manifest rename (breaking, needs a plan); a complaint about a *missing*
   attribute is H3 and the repair is a design decision, not a patch.
