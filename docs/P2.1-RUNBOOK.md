# Relay P2.1 — deployment runbook for the app-owned closure field

This supersedes §8 of `docs/P2-INTEGRATION.md`. It assumes the Phase 2 code is on
the branch and the manifest declares the `jira:customField` module.

Nothing in this runbook was executed here. The sandbox has no Atlassian network:
`npx @forge lint`, `deploy`, `install`, and every REST call are **BLOCKED**. The
steps below are the ones that must run on your machine.

---

## What changed, in one paragraph

The customer closure condition used to read a **Number field an administrator
created by hand**, whose id had to be typed into the manifest. Relay now declares
its **own read-only number field** (`jira:customField`, key `relay-closure-count`),
writes it through `PUT /rest/api/3/app/field/{fieldIdOrKey}/value`, reads it back,
and resolves its identifier at runtime instead of being told it. The condition
expression still has to contain the numeric id — Jira expressions are static — but
the id is now **discovered by the app and printed for you**, never guessed.

---

## Step 0 — build and check, locally

```bash
cd app
npm install                     # only if app/node_modules is missing
npm --prefix ui install         # only if app/ui/node_modules is missing
npm test                        # 99 tests, 0 failures
cd ui && npx tsc --noEmit && npm run check:render && npx vite build && cd ..
```

`vite build` writes `app/static/relay`, which the manifest's `relay-ui` resource
points at. A local build is not a deployment.

## Step 1 — register once, with the product's own identity

```bash
npx --yes @forge/cli login
npx --yes @forge/cli register   # writes a real app id into app/manifest.yml
```

`register` rewrites the placeholder `id:` in `manifest.yml`. **Do not commit that
line.** The app must be a different registration from `relay-phase0-probe`.

## Step 2 — first deploy and install

```bash
npx --yes @forge/cli deploy
npx --yes @forge/cli install --site onepes930.atlassian.net --product jira --environment development
```

At deploy time Forge creates the field (a single locked instance of the module)
and Jira assigns it a numeric id. That id does not exist before this step, which
is why it cannot be in the repository.

## Step 3 — find out what the field is, from the app itself

Open the app on the site (global page → **Settings → Enforcement → Closure
field**). It shows:

- the resolved `customfield_NNNNN`,
- the field key Jira generated,
- the module type id (`…/static/relay-closure-count`),
- **Condition expression**, with a **Copy line** button.

If it says **Not resolved**, the app could not find its own field. Stop here and
check that the manifest's `jira:customField` module deployed (Jira → Settings →
Issues → Fields should list "Relay open commitments" with a lock on it).

The same values are available without the UI:

```bash
# from a terminal, with the app deployed, this is the resolver the console calls:
#   relay.field.resolve
# it returns { field: { id, key, typeId, resolved, expression, manifestLine }, … }
```

## Step 4 — put the id into the condition expression, then deploy again

In `app/manifest.yml`, replace the placeholder line:

```yaml
      expression: "issue.customfield_relay_closure_count == 0"
```

with the line the console printed, for example:

```yaml
      expression: "issue.customfield_10123 == 0"
```

Then:

```bash
npx --yes @forge/cli deploy
```

Back in Settings → Enforcement, press **Record as deployed**. That stores the
expression string in Relay's settings and stops the console warning that the
manifest may still name the placeholder. Relay cannot read a manifest from inside
Jira, so this records your statement, not a verification.

## Step 5 — make the field part of the project's field configuration

Jira → Project settings → **Screens** for the `FS` issue types used for repairs:
add **Relay open commitments** to the default screen (or the screen used by the
closure transition).

Why this matters: Jira expressions return **null for any field hidden in the
field configuration active for the issue**. A hidden field is indistinguishable
from an empty one inside the condition, and Relay's condition treats null as a
refusal — the portal would refuse everyone. Read-only fields are not rendered on
issue create, transition, or portal request screens, but they still have to be
configured on a screen to be part of the field configuration.

This is the single most likely way to get a working app that refuses everything.

## Step 6 — reconcile before you attach anything

Settings → Enforcement → **Reconcile every case**. It walks every tracked issue,
re-derives the projection and the field from the ledger, and reports what it
repaired and what it could not.

Or, per issue: **Check one case**, which reconciles one issue and then reports the
gate decision, the projection, the field value and any disagreement between them.

Nothing is attached to a workflow yet, so nothing has changed for users.

## Step 7 — attach the two enforcement modules to the closure transition

In the `FS` workflow, on the transition that closes a request:

1. **Validators** → add **Relay closure gate**. It blocks agents and the REST API
   and can write a message naming what is outstanding.
2. **Conditions** → add **Relay closure readiness**. It gates the customer portal
   and cannot explain itself.

Both are company-managed-only modules.

## Step 8 — walk the twelve steps on a real `FS` issue

Load → scan comments → accept a candidate → reload → Case Workspace → change the
owner → closure refused → verify → the field and the projection both reach 0 →
closure permitted. Then test the three paths separately:

| Path | What proves it | Expected |
| --- | --- | --- |
| Agent transition button | validator | hidden/blocked with Relay's message |
| `POST /rest/api/3/issue/{key}/transitions` | validator | HTTP 400, message names the counts |
| Customer portal | condition | transition absent or refused, **no message** |

The portal path is only proven once you have watched it refuse with the condition
attached. Do not infer it from the field value.

## Step 9 — what to do when it misbehaves

| Symptom | Likely cause | Where to look |
| --- | --- | --- |
| Console says **Not resolved** | custom field module not deployed, or the app was installed before the module existed | Jira → Fields; redeploy; reopen Settings |
| Console says **Not verified** next to the condition | expected: an app cannot read a workflow's configuration | the workflow editor |
| Portal refuses **everything**, even closed-out requests | the field is hidden in the project's field configuration, or the expression still names the placeholder | Steps 4 and 5 |
| Portal **allows** closure that should be blocked | the condition is not attached, or is attached to the wrong transition | workflow editor; then Step 8 |
| `field_write_unverified` in the console | Jira accepted the write (204) but the value did not change | Settings → Reconcile every case; if it persists, check the field is not on a locked screen that strips writes |
| `not_field_owner_or_missing_scope` (403) | the app is not the field's owner, or `write:app-data:jira` was not consented at install | manifest scopes; reinstall with `--upgrade` |

## Scope and identity summary

| Item | Value | Where it comes from |
| --- | --- | --- |
| Field module key | `relay-closure-count` | `app/manifest.yml` |
| Field type id | `ari:cloud:ecosystem::extension/{appId}/{environmentId}/static/relay-closure-count` | derived at runtime from the invocation's `localId` |
| Field id | `customfield_NNNNN` | Jira, discovered via `GET /rest/api/3/field` matching `schema.custom` |
| Write endpoint | `PUT /rest/api/3/app/field/{fieldId}/value` | private app-field API |
| Write scope | `write:app-data:jira` | declared in the manifest; documented as optional today, planned to become mandatory |
| Read scope | `read:jira-work` | field read-back |
| Condition expression | `issue.customfield_NNNNN == 0` | `app/src/field.js`, printed by the console |

## What is still manual, and why

1. Registering the app (once) — identity cannot be generated for you.
2. Deploying — no deployment happens from this environment.
3. Pasting the resolved field id into `manifest.yml` and redeploying — a Jira
   expression is a static string evaluated by Jira; it cannot resolve a field at
   evaluation time. Relay removes the guessing, not the step.
4. Adding the field to a screen — an administrator action inside Jira.
5. Attaching the validator and the condition to the transition — an administrator
   action inside Jira.
6. Pressing **Record as deployed** so the console stops warning — a statement by
   the operator, because an app cannot read a workflow's configuration.
